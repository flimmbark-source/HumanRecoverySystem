# Weave Operational Studio

## Product and release target

Weave is the researcher's workspace from fieldwork to decision. For the first release, support one focused workflow per project and multiple private projects per organization. The pilot workflow starts with scope and ends with a current-state map, prioritized opportunity sheet and leadership brief. The earlier ESRA proposal calls for about 6–8 voluntary interviews, 1–2 walkthroughs and roughly four weeks, subject to agreement. Actual workflow, participants and measured baselines are still open. Voluntary discovery ends with recommendations. Any subsequent delivery for ESRA is separately scoped and paid.

**Confirmed direction.** Graph-based capture, layered and generated connection descriptions, field evidence and synthesis, static and timeline views, scenario branches, and separate treatment of time, money and human outcomes. Both researcher-gathered and agent-found evidence feed the work. Wide and deep research support different decisions.

**Research principle.** Learn how people contribute by observing them in the act of doing the work. Record what they do effectively, where they struggle, and the conditions around both. Talk through what you saw with the person to understand effort, preferences, and context that observation alone can miss. Keep synthesis open-ended. An insight can arise anywhere and can enter Weave before anyone links it to evidence. The pilot uses those insights to strengthen the existing organization and improve people's working lives through focused improvements that protect what already works.

**Current reference.** v0.7 supersedes prior layout. It demonstrates the interaction with synthetic data, local storage and manually imported agent suggestions. Preserve the interaction, use the spec for data semantics and repair the known prototype limitations in the implementation sequence.

**Proposed release defaults.** Private responsive web app with a deployable server and SQL-backed project data. Desktop for deep mapping and editing, mobile for quick capture, map navigation and inspection. Start with owner, researcher/editor and reader capabilities. Use application configuration for hosting, email/auth, database and research provider. Billing, leased client tools and general B2B pipeline automation are later products. Weave records potential implementation options and validation plans.

## Workflow and interaction

1. **Start a project.** Choose blank or synthetic demo. Capture workflow name, research question, organization or unit, scope description, start, intended outcome and known external interfaces. Start with two meaningful nodes and a quiet canvas. Support working drafts and easy movement between projects.
2. **Map the work.** Create/rename/move/group nodes of type person/role, system, resource, output or group. Distinguish work within scope, external actors with direct interfaces, and contextual items that can be filtered. Connect nodes by click/drag or a keyboard/list form. Support pan, zoom, fit, focused neighborhood, search, filters, an undoable Tidy, and undo/redo for model edits. Preserve label and node spacing under drag, resize and Tidy. Display external scope on each affected node with border treatment and an explicit label. The dotted canvas grid may remain. Avoid a dashed rectangle around the graph.
3. **Read a connection in layers.** On the map show the short label and optional compact timing/evidence hint. Active/hover/focus/tap treatment identifies the line and endpoints. In the inspector show the connection type, source → destination, a plain-language sentence, then a compact input → action/performer → output sequence. Use consistent token colors for actor, action, item and state, with text labels and accessible contrast. Provide collapsed Performance and Evidence sections and a separate Edit disclosure. Editing structured fields updates the summary and candidate preview immediately. Reuse the same sentence logic in the timeline, report, and research proposals. Keep the current selection across editing, evidence capture and mode changes where it still exists. Mobile uses a sheet or drawer that leaves the map usable when closed.
4. **Capture and synthesize.** Start an interview, observation or walkthrough session with anonymous source ID, participant role, date and collection. Capture one line from an already selected node, edge or activity, or the unassigned inbox. Save with keyboard or touch and inherit session context. Offer optional work episode details: task and intended outcome, what the person actually did, conditions that helped or hindered them, what happened, and any hidden effort, workaround or support. A researcher can distinguish what they observed from what a participant reported. Keep work linked to its context and avoid individual skills scores or fixed deficit labels. Allow multiline paste with a split preview. Use sticky-style cards with category and optional color, nest/group by collection/theme, filter by source/type, and show counts or pins on the map. Provide a standalone freeform insight editor that can save with no source, model target, category, or template. Accept ideas from a conversation, a sketch, prior experience or independent reflection. Let researchers add, revise or remove evidence links later and preserve raw notes when interpretations change. Link notes and insights with support, contradiction, relatedness or possible cause. Keep evidence status visible when an insight is cited in a recommendation. With incomplete evidence, present that recommendation as a hypothesis to test and identify what would clarify it.
5. **Trace a case.** Structure view is the editable graph. Timeline plays, pauses, scrubs, steps and loops a selected ordered route through it. Show the active item, activity and state transition, and distinguish work from waiting. Users explicitly choose branches or create named routes. Identify gaps, branches and cycles. Require explicitly ordered occurrences for a repeat/rework loop and bound playback. A route requires valid adjacent edges, a start and an outcome and can contain named internal activities. Show illustrative playback with an incomplete timing label when measurements are missing. Flag information or dependency links that can affect the route even if route effort excludes them.
6. **Propose a change.** From an insight, option or blank hypothesis, branch from a pinned baseline revision or from a previous scenario revision. Allow structural edits directly to nodes, connections, activities, selected routes and assumptions. Display selected comparison and lineage. Offer parent and original-baseline comparison for successive changes, highlighting added/removed/changed nodes and links and explicitly affected actors, inputs, downstream dependencies and outputs. Surface broken handoffs, unreachable outcomes, changed responsibilities and unresolved impacts. Recompute supported values on edits. A flagged downstream item is a place to investigate. Preserve baseline and sibling data and evidence attachments.
7. **Make the decision.** Provide an opportunity register and selected recommendations. Compare maintaining the current approach, process/policy changes, existing tools, and a bespoke tool when justified. Users choose prioritization and can use criteria-based sorting for evidence strength, effort, expected value and human risk. Tie each row to relevant evidence, graph objects and scenarios as available. Show what already works and deserves protection, the smallest reversible change that could help, and whose working day changes. For each proposal, include benefits, downsides, added or shifted work, implementation effort, costs, tradeoffs, confidence, unknowns and what to test. Make it possible to explore broad ideas in a scenario while treating focused improvements within the existing structure as the pilot's recommendation scope. Review any proposed shift in responsibilities with the people affected, including their preferences and available support. Preview and export an anonymized leadership brief and current-state map as print-ready PDF, and the opportunity sheet as XLSX or CSV, plus workspace JSON for transfer/backup. Use role- or workflow-level findings in leadership materials and omit detail that could identify participants in small teams. Expand citations to approved anonymous source IDs or public URLs in the allowed export.

## Data contract

Use stable IDs with versioned schemas and validated references. Model these concepts. The names and storage layout can follow repository conventions.

| Record | Essential fields |
| --- | --- |
| Organization, project and membership | Organization ID, user's membership and role, project ID, workflow scope, owner, status, current baseline revision |
| Node | Stable identity, kind, label, role/description, scope relation, optional parent group, position |
| Connection | Endpoint IDs, type, human-readable label, directedness, optional linked activity, work item/input/output state, result, applicability/conditions and exceptions |
| Activity | Internal or attached to a connection, performer/owner ID distinct from sender and recipient, explicit action code, input/output, inclusion in workload, measurements |
| Measurement/assumption | Metric, numeric value or range or unknown, unit, denominator and period, date, sample size/method where applicable, source IDs, basis and status, effect direction when used as a guardrail |
| Route | Start/end, ordered edge and/or internal activity occurrences, names, explicit repeats or branches |
| Session/source | Anonymous ID, type, role/date, permission scope for use, approved excerpt or public URL/date, separate export visibility |
| Note and evidence link | Text, type, group/color, source and evidence status, anchored target and version/context, optional work episode details, typed support/contradiction/association with another note or insight |
| Insight, opportunity, option, recommendation | Freeform insight with optional evidence and model links added or edited independently. Opportunities and recommendations can cite insights, evidence and scenario revisions, with separate fields for interpretation, remaining uncertainty, what to preserve, stakeholders, decision state, and a validation plan |
| Revision and scenario | Immutable base/parent revision references, model and assumptions, audit attribution, review status, restoration metadata |
| Research run and candidate | Mode, revision/input provenance, status, output schema version, candidate ID, basis, proposed model diff, reviewer and disposition |

**Connections.** Work flow (solid with directional arrow), information/communication (dashed), dependency/prerequisite (dotted), authority/responsibility (distinct line/marker and text), association (neutral, undirected by default). Include all types in the legend. Source means where the handoff originates. Performer is an explicit action owner and can be the sender, receiver, a third party or unknown. Model item, input state, action, output state and produced result separately. Use deterministic typed sentence segments for highlighting. Missing parts stay visible on demand. Example from the synthetic workflow: “The application moves from Application form to Coordinator, who reviews it and changes its state from submitted to ready for placement.” Never assign action from link direction or use prose as the source of truth. Keep notes and descriptions searchable.

**Revision integrity.** Separate graph layout edits from operational content revision changes. Use one authoritative record for duration and recurrence so the connection and its associated activity cannot disagree or double count. Make accepted evidence relationships durable across removals: resolve a removed target as historical or unassigned, preserving its source and the baseline attachment when deleting in a scenario. Preview and validate imports, including older supported records, with field-level errors and no partial writes. Import prototype exports with `format: weave-operational-model`, `exportVersion: 2`, including the supplied v0.7 fixture. Preserve IDs/references, node positions, source notes, scenarios and assessments. Report individual legacy records that require a user decision, including duplicated timing fields that disagree and defaulted zeros where the original observation basis is unknown. Export importable versioned JSON. Import to a new project by default. Any replacement requires an explicit preview and backup.

## Impact engine

- **Effort.** For included activities, active minutes per occurrence × expected occurrences per case. Sum without counting a handoff and its attached activity twice. Monthly hours = minutes per case × monthly cases / 60. Known contribution and missing inputs must stay visible. If frequency or volume is unknown, propagate the uncertainty. For disjoint routes, report per route and combine only when appropriate case weights are available. Distinguish before/after volume effect from like-for-like efficiency by providing a common-volume comparison. Group workload by role and retain an unassigned category.
- **Elapsed time.** On an explicit sequential route, use active plus waiting for the selected occurrences. Keep route time apart from total staff effort. Model parallel overlap or queue effects only if the data model explicitly supports them. Show changed dependencies and downstream risks when a quantitative impact is unavailable.
- **Financial impact.** Show assumptions, horizon and currency. Separate time capacity, actual cash, one-time implementation cost and ongoing costs. If the user supplies an applicable rate, show value of released time as a modeled capacity estimate. Count cash savings only from a documented cost mechanism, such as fewer paid overtime hours or a retired invoice. Show recurring net cash, and payback when one-time cost and positive recurring net benefit are known and periods are compatible.
- **Human and service impact.** Capture who benefits, who takes on extra work or loses contact, likely failure modes and both positive and negative effects on accessibility, relationships and quality. Include testable guardrails with metric, denominator, baseline period, proposed target/threshold, owner, collection method, follow-up date and rollback trigger where appropriate. Examples include retention, first-contact resolution, or requests for a human follow-up. Keep qualitative risks visible with an unknown numeric magnitude. Only produce numerical customer/service changes from entered evidence or explicitly labeled assumptions with a supported calculation.
- **Working conditions.** Compare the working day across the affected roles. Track chosen indicators such as interruptions, after-hours work, unplanned coverage, or time available for work where people add value. Consider whether a proposal concentrates more work on someone already providing backup or shifts a burden to another person. Check service quality and workload together in a small trial. Record participants' feedback and a way to reverse the change.
- **Traceable comparisons.** Show absolute baseline and proposed values, delta, units, assumptions, as-of date and source. Tag measured, reported, estimated, assumed or unknown. Preserve pre/post observations separately from modeled estimates. Reviewers should be able to open each input from a result. Recompute when inputs change and surface stale dependent recommendations if cited inputs or revisions change.

## Research jobs and human review

**Wide research** turns a question, workflow scope or approved public topics into sourced patterns, gaps, comparable practices and existing solutions. Record direct source URLs, retrieval dates, relevant excerpts, what each option covers, where the evidence falls short, and gaps worth checking with participants. Public signals can inform an inquiry. Internal claims require internal evidence. Include a reviewable recommendation to investigate, test an existing solution, or close the opportunity with a reason. A close recommendation must show coverage against the observed workflow, remaining fit gaps and uncertainty. A reviewer can reopen it.

**Deep research** takes a selected insight or set of approved de-identified notes, a baseline revision and a question. It can extract candidate nodes, relationships, activities and observations, reconcile source disagreements into review items, recommend measurement targets or falsification questions, and investigate alternatives. Both human fieldwork and wide findings can trigger deep research. Suggestions for the next inquiry are editable by the researcher.

Researcher-authored synthesis can happen independently of the agent workflow. Keep the agent candidate schema and provenance checks for agent-generated proposals. The freeform insight editor needs its own save path, including for early thoughts with no source link. When an agent explores an insight, surface contextual explanations and missing evidence. Treat inferred contributions as hypotheses about the work and its conditions.

Use a server-side adapter for a configurable real research provider with public search for wide jobs. Keep fixture/test providers visibly labeled. Base the extraction/prompt contract on the supplied skill, accept v1 candidate JSON, and version any extension for new proposal types. Validate schema, source reference, field bounds, IDs and tenant access at review and acceptance. Each candidate has proposed change, target, basis/excerpt, certainty, source date, and review status. Reviewers can edit, accept, reject, or mark needing evidence. Detect duplicates and stale revisions. Accept with a single authorized, idempotent transaction and human attribution. Keep job results and dispositions after refresh.

Jobs support queued, running, ready for review, failed and cancelled states, provenance, a time/work budget, bounded retries and visible errors. Choose approved excerpts before submitting them. Treat public or retrieved content as data. Cap time/cost and send only authorized inputs. No agent access to confidential transcripts or private beneficiary records, outbound contact, purchasing, public publication or direct operational writes. With no provider configured, research capture, manual review and candidate import remain available.

## Implementation sequence

1. **Foundation and compatibility.** Inspect reference assets and baseline export. Establish schema, migrations, auth/project scopes, save and recovery, import/export, synthetic seed and deterministic domain services. Prefer the repo stack. For a blank repo, a TypeScript React/Next.js app and PostgreSQL are a sensible default. Choose a maintained graph library or port the SVG interaction where fidelity requires it. Queue through the database or existing infrastructure.
2. **Researcher's daily loop.** Implement the v0.7 map and inspector with credible keyboard and touch access. Complete mapping, capture, an inbox, note links and evidence-backed insights. Then connect versioned scenarios, routes, playback and impact. Fix v0.7’s shared-note mutation across scenarios, first-branch playback fallback, and the duplicate timing data. Test each with legacy and fresh records.
3. **Research and delivery.** Implement wide/deep requests, job recovery, candidate validation/review, option comparison and anonymized reports. Finish the complete flow on synthetic data. Give researchers a usable error/recovery state for invalid import, failed autosave, stale edit, a failed provider call and an empty project.

During the synthetic walkthrough, record the sequence and time taken for quick capture, synthesis and report generation so the pilot team has a repeatable way to measure its own research effort. Treat any comparison to a previous manual workflow as unmeasured until a comparable timed run exists.

Use transactional, access-controlled persistence and optimistic revision checks. Keep tenant data private by default. Use separate per-user view state for pan and selection. On autosave, show saving/saved/failed and preserve a recoverable draft across transient errors. Provide a project export and document DB backup/restore with a tested procedure. Use environment secrets, explicit input size limits and restart-safe jobs. Do not place source excerpts in routine logs or enable public report links by default. Provide `README` setup, migrations, seed, `.env.example`, tests, production build and deployment docs. Build and test locally or on a private preview using synthetic data. Actual hosting, provider, repository and client policy are open integration decisions.
